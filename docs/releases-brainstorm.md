## Framing: two kinds of open data, one thin engine

The core idea: a deck is data, a template is data, and the engine is a replaceable function from the two to pixels.

Today those three live in one directory, and `slide_generator.rb` finds them by constant (`TEMPLATE_CATALOG_PATH`, `BRANDS_DIR`, the `decks/*.yml` glob in `Rakefile`).
The proposal is to give each its own repo, name the interface between them, and make the static site a second consumer of the same interface.

### Repo boundaries

| Repo | Holds | Changes when |
|---|---|---|
| `slides-decks` (content) | `decks/*.yml`, `assets/<deck>/*` (images a deck references), `index.json` | a message changes |
| `slides-templates` (form) | `catalog.yml`, `templates/*.html.erb` + `styles.css`, `brands/<name>/brand.yml` + logo, `previews/<brand>/<template>.png`, `manifest.json` | the visual language changes |
| `slides` (engine + site) | `slide_generator.rb`, `lib/`, `Rakefile`, `test/`, `public/index.html` | the renderer or the viewer changes |

The two data repos are the API.
The engine and the site are two clients of it; a Jekyll site (`~/workspace/civic-studio-website`, already on GitHub under `civicstudio/`) can be a third.

Why not two repos (engine + templates together, decks apart)?
It works, and it is the smaller first step, but then "contribute a brand" means a PR into Ruby code, and the site cannot describe templates without also describing the engine.
Splitting form from engine on day one costs one env var and keeps the promise that templates are data.

### The interface

1. `slides-decks/index.json`: one entry per deck, generated by the engine, committed.
2. `slides-templates/manifest.json`: templates, regions, brands, previews; generated from `catalog.yml` and `brands/`, committed.
3. Deck files keep `version: 2`; each manifest carries `schema: "slides/decks@1"` or `"slides/templates@1"`.
   A deck may pin `templates: ">=1"`; the engine and site refuse a manifest whose major version they do not know.
4. Engine locates the data repos through `SLIDES_DECKS_DIR` and `SLIDES_TEMPLATES_DIR`, defaulting to sibling checkouts (`../slides-decks`, `../slides-templates`).
   Unset and missing paths fail loudly with the path they tried.
   Git submodules are the alternative; they would pin versions, at the cost of every LLM session having to remember `git submodule update`.
5. The site reads a `sources.json` next to `index.html` that names the two manifests by URL.
   Release 1 uses `raw.githubusercontent.com/<org>/<repo>/main/...` (no CORS problem, roughly five-minute cache).
   Later releases can point the same `sources.json` at a tag (`/v1.2.0/`) or at a build-time copy.
   A build step (Actions copies both manifests into `public/`) is more deterministic but goes stale until someone rebuilds; raw URLs are live and need no Actions.

### "Templates as a set of images conformant to a size, with a manifest"

Two readings.

**Reading A: preview and regions.**
A template entry is the existing `catalog.yml` spec (fields, constraints, `regions` as canvas fractions) plus one 1920x1080 PNG per brand showing the template with placeholder content.
The engine keeps rendering from `templates/*.html.erb`; the image is derived, and a test asserts it is exactly canvas size.
`lib/brand_sheet.rb` already renders every template in every brand, so previews are a crop of what `rake slides:sheet` produces.

- Pro: honest to the pipeline, zero new rendering paths, and the site can build a picker from images plus region boxes with no template engine in the browser.
- Con: the image is documentation, not the template; a designer still edits HTML/CSS to change the form.

**Reading B: background plates.**
A template is a full-canvas image (PNG or SVG, exported from Figma, Canva, or a paint program) and a manifest of text regions laid over it.
The engine positions text into the regions with `position: absolute` and the brand's type tokens.

- Pro: anyone who can make a 1920x1080 image can contribute a template, no HTML.
- Con: a plate is brand-specific (a template x brand product, so the preview matrix becomes the source), the social formats (`catalog.yml` `social_formats`) each need their own plate or accept cropping, and overflow cannot reflow because regions are fixed boxes.

Recommendation: Reading A in Release 1, and add Reading B as a second template kind (`kind: plate` in the manifest) when community templates arrive (Release 6).
Both readings share the manifest shape, which is the point of naming the interface now.

## Release 1: Published

One-line goal: the data is on GitHub, the site reads it, and nothing on the site depends on a local render.

### Ships

- Three GitHub repos with history: `slides-decks`, `slides-templates`, `slides`.
- `slides-decks/index.json` and `slides-templates/manifest.json`, generated and committed.
- Engine reads data repos via `SLIDES_DECKS_DIR` and `SLIDES_TEMPLATES_DIR`.
- `public/index.html` served by GitHub Pages from the `slides` repo, reading both manifests through `sources.json`.
  The existing YAML panel and client-side preview stay; the thumbnail strip hides when a deck has no `renders` entry rather than showing broken images.
- Template previews (Reading A) at canvas size, one per brand per template.

### Explicitly out

In-browser editing, PRs from the UI, CI rendering, PNG/PDF on the site, brand or template picker UX, LLM integration, embed snippet, Google Slides, plates (Reading B), migrating the 10 inline-theme decks to brands.

### Stories

- Story R1.1: Content repo.
  As a deck author, my decks live in `slides-decks/decks/*.yml` and `rake slides:index` writes `index.json` from the YAML alone, not from rendered PNGs.
  Test: `test/index_test.rb` asserts every `decks/*.yml` appears with `title`, `brand`, `slide_count`, `templates`, and `path`, and that the JSON validates against `schema/index.schema.json`.
- Story R1.2: Templates repo.
  As a brand maintainer, `catalog.yml`, `templates/`, and `brands/` live in `slides-templates`, and `rake slides:templates_manifest` writes `manifest.json` with one preview per brand per template.
  Test: `test/templates_manifest_test.rb` asserts every `templates/*.html.erb` has an entry, every entry's `regions` matches `catalog.yml`, and every listed preview exists and its PNG header reads exactly `canvas.width` x `canvas.height`.
- Story R1.3: Engine finds the data.
  As an LLM session, `rake slides:generate[govcenter]` works with the two env vars set or the sibling checkouts present, and fails naming the missing path otherwise.
  Test: `test/paths_test.rb` sets each var to a temp dir and asserts the error message contains the path; the existing `test/brand_test.rb` passes unchanged against the moved `brands/`.
- Story R1.4: Site reads the manifests.
  As a visitor, `index.html` loads `sources.json`, lists every deck from `index.json`, shows its YAML and client-side preview, and lists every template and brand from `manifest.json` with its preview image.
  Test: `test/site_test.rb` serves `public/` plus fixture manifests on a local port and drives Chrome (same Puppeteer as `lib/render.cjs`) to assert the deck select has N options and the template gallery has M images.
- Story R1.5: Published, with explicit success.
  As Ryan, `bin/verify-release` fetches the Pages URL and both raw manifest URLs, parses them, and prints each URL with its status and entry count; any non-200 or parse failure exits 1.
  Test: the script itself is the test; it runs after every push and its output is pasted into the release note.

## Releases 2 to 6

### Release 2: Pick (templates and brands as a gallery)

Theme: the site becomes the place to choose form.

- Stories: browse templates by brand with region boxes drawn over the preview; open a deck and see, per slide, which template it uses and the brand sheet; switch the preview brand for a deck without editing it (client-side, reads `brand.yml` tokens from the templates repo).
- Unlocks: a brand picker for the GovCenter deck and any future client deck; previews that double as documentation for LLM sessions.
- Depends on: R1.2 (manifest with previews and regions).
- Note: the "switch brand" story is the moment to retire the viewer's inline `SLIDE_CSS` and fetch `styles.css` plus `brand.yml` from the templates repo, so the browser preview uses the same tokens as Chrome.

### Release 3: Render in CI (renders as data, lint as a gate)

Theme: no local Chrome required to see a finished slide.

- Stories: a push to `slides-decks` runs `slides:lint` and schema validation and fails the PR on overflow; a merge renders PNG and PDF for changed decks and publishes them (Pages artifact of the decks repo, or a `renders/` branch) and writes their URLs into `index.json` under `renders`; the site's thumbnail strip reads those URLs.
- Unlocks: thumbnails and PDFs on the site, an audit log (git history of the decks repo is the change log, CI status is the quality log), and the GovCenter deck's acceptance ("renders with the repo's usual tooling") becomes a CI check.
- Depends on: R1; `lib/render.cjs` already runs headless, so the Action is `npm ci` plus `bundle exec rake`.
- Decision inside: renders in git (simple, grows the repo) versus artifacts (clean, expire unless promoted to Pages).

### Release 4: Edit (the page manages the YAML)

Theme: the bit of UX that manages open data.

- Stories, lite path: edit a deck's YAML in the browser with live preview; "Propose" opens GitHub's own editor at `github.com/<org>/slides-decks/edit/main/decks/<deck>.yml`, and for a new deck `github.com/<org>/slides-decks/new/main/decks?filename=<name>.yml&value=<yaml>`; GitHub handles the fork, branch, and PR, and R3's CI lints it.
- Stories, full path: the site creates the branch and PR itself through the GitHub API.
  A static page cannot hold a secret, so this needs the device flow with a fine-grained token stored in the browser, or a small worker that holds the OAuth secret.
- Unlocks: git history as the audit log of every deck change, made from a phone.
- Depends on: R2 (browser preview shares tokens with Chrome, or edits will look wrong) and R3 (CI validates what the UI proposes).
- Recommendation: ship the lite path; it delivers "PR from the UI" with zero auth code.

### Release 5: Assist (LLM loop against catalog and lint)

Theme: the maintenance model is a session, so give the session tools.

- Stories: `rake slides:prompt_context` output is published as `slides-templates/PROMPT.md` and linked from the site, so any LLM can author a conforming deck; a `slides` skill (or MCP tool) exposes `lint`, `index`, and `generate`, and the loop is author, lint, split, repeat; the site's editor has an "ask" box that produces a YAML diff and runs the lint before proposing.
- Unlocks: decks maintained by conversation with a hard stop on overflow; new client decks in one session.
- Depends on: R3 (lint in CI so the loop's output is checked twice) and R4 lite (somewhere to send the diff).
- Note: most of this exists offline today (`prompt_context`, `lint`); the release is about publishing it and wiring it to the site.

### Release 6: Share (embed, export, contribute)

Theme: other sites and other people.

- Stories: an embed snippet (`<iframe src="…/#deck=govcenter">` or a web component reading `index.json`) used by `civic-studio-website` and GovCenter; `civic-studio-website/_data/decks.json` fetched at build from `index.json` so the Jekyll site lists decks; Google Slides one-way export (PLAN.md Story 16: one full-bleed PNG per slide, notes into speaker notes) as an Action on the decks repo; community brands and templates by PR, validated in CI against the templates schema, including Reading B plates (`kind: plate`).
- Unlocks: decks as a public record of Civic Studio's thinking, and templates from people who do not write CSS.
- Depends on: R3 (rendered PNG URLs to embed and to upload to Google Slides) and R1.2 (a schema to validate contributions against).

## Open questions for Ryan

1. Three repos now, or two?
   Two (`slides` with templates inside, `slides-decks`) is a smaller first push; three keeps templates out of Ruby code from day one.
2. Which org: `civicstudio` (where `civic-studio-website` lives) or personal?
   The raw URLs in `sources.json` bake this in.
3. Which decks are public?
   Several decks read as client or pitch material (the list is in `~/workspace/slide-decks/PLAN.md`).
   Same schema, a second private `slides-decks-private` repo, and the site lists only what it can fetch.
4. Is the browser preview an approximation or a second truth?
   If a second truth, switch templates from ERB to a logic-less language (Liquid runs in Ruby and JS) so one file renders in both; if an approximation, keep ERB and add a screenshot-diff test in R2.
5. Renders in git or in artifacts (R3)?

## Recommendation

Order: R1 Published, R3 Render in CI, R2 Pick, R4 Edit (lite), R5 Assist, R6 Share.

R3 before R2 because thumbnails and a lint gate make every later release safer, and the CI is mostly `render.cjs` in a container.
R4 lite rides on GitHub's own editor, so it is cheap once R2 and R3 exist.

If only three releases: R1, R3, and R2, with R4's lite path folded into R2 as a single "Edit on GitHub" link per deck.
Cut R5 (the offline loop already works through `prompt_context` and `lint`), R6, and the full-API path of R4.

First concrete step, before any of this: make the first commit in `~/workspace/slides`, and update PLAN.md `## Now` to say lint is done.
